# AdzOnRoad Taxi Company Portal Skill

## What this portal is and who uses it

A fourth role alongside Advertiser/Admin/Driver: the taxi company that owns the vehicle fleet and employs the drivers. They register their cars and drivers, see fleet-wide status/earnings/GPS, and manage per-vehicle maintenance — distinct from an individual `Driver` (who manages just their own shift) and from `Admin` (platform-wide, all companies). One `TaxiCompanyProfile` mock company (`MOCK_TAXI_COMPANY` — Cedar Taxi Services) owns the whole fleet shown on the dashboard; there's no multi-tenant switching.

Uses the **global navy/amber theme** (`tokens` from `../theme`) via `DashboardShell`, the same as Admin — this portal was **not** given its own scoped design system the way the Advertiser portal was (see [design-system skill](../design-system/SKILL.md)). The brief for this portal only specified functionality, not a distinct visual identity, so it stays on the shared palette. Don't introduce a local `advTokens`-style theme file here unless explicitly asked.

## Signup/verification and login

- **Signup** (`SignupPage.tsx`, role `taxiCompany`): Company name, Email, Mobile number, Region (select from [src/data/lebanonRegions.ts](../../../src/data/lebanonRegions.ts)), Password. On submit, the page does **not** navigate to the dashboard — it swaps to a "pending verification" confirmation panel in place (`pendingVerification` local state), since taxi companies are reviewed before activation. This is the one signup role that behaves this way; advertiser/driver signup still redirect straight to their dashboard. If asked to add a real verification backend, that's from-scratch work — there's no persistence, the "submitted" state resets on page reload.
- **Login** (`LoginPage.tsx`, role `taxiCompany`): the identifier field label/type changes to "Email or mobile number" (`type="text"`, not `type="email"`) specifically for this role — every other role still just has "Email". Both pages type-share `AuthRole`/`AuthLayout` ([src/layouts/AuthLayout.tsx](../../../src/layouts/AuthLayout.tsx)) — `taxiCompany` is a real member of that union now, not a special case bolted on separately.
- The Homepage's existing "Partner Your Fleet" CTA (in the `#taxi-companies` section) now correctly links to `/signup?role=taxiCompany` — it used to point at `/signup?role=driver` as a placeholder from before this portal existed. If you see any other stale `role=driver` fallback meant for taxi companies elsewhere, it's leftover from the same gap.

## Data model

[src/types/taxiCompany.ts](../../../src/types/taxiCompany.ts) + [src/data/taxiCompanyMockData.ts](../../../src/data/taxiCompanyMockData.ts), following the same types+data split as Advertiser/Admin/Driver. Key types: `Car` (plate, category, type, model, year, papers image name, status, GPS status, screen fields, driving/screen-time/distance-today stats, `lat`/`lng`), `CompanyDriver` (name, mobile, ID/license image names, assigned car, status), `FleetEarnings`, `SupportContact`.

**`PlateCategory` is a reasonable mock categorization, not a legal reference** — Lebanese plates are actually distinguished by color/series (red for public/taxi, etc.) rather than a printed letter code the way the brief's phrase "plate character" might suggest. The five categories used (`Private`, `Public (Taxi — Red)`, `Rental (Green)`, `Transit`, `Diplomatic`) are a plausible, clearly-labeled approximation for a mock form field, not something to treat as authoritative if a real plate-validation feature is requested later — flag that assumption to the user if it matters for a real implementation.

Only `CARS` and `DRIVERS` are meant to be mutated at runtime (via the dashboard's local `useState`, see below) — `MOCK_TAXI_COMPANY`, `FLEET_EARNINGS`, `SUPPORT_CONTACT` are static fixtures like elsewhere in the app.

## Page structure — a layout route, unlike the other portals

All 8 sidebar items are **real routed pages** under [src/pages/taxiCompany/](../../../src/pages/taxiCompany/): `OverviewPage` (index), `CarsPage`, `DriversPage`, `EarningsPage`, `ScreensPage`, `ReportsPage`, `SupportPage`, `SettingsPage`. Nothing in this sidebar is a `useToast` stub.

**This portal uses a react-router layout route, and the Advertiser portal does not — don't copy the Advertiser pattern here.** [TaxiCompanyLayout.tsx](../../../src/components/taxiCompany/TaxiCompanyLayout.tsx) is registered as `<Route path="/taxi-company" element={<TaxiCompanyLayout />}>` with the 8 pages as child routes rendering into its `<Outlet />`. The Advertiser portal instead has every page render its own `<AdvertiserLayout>` wrapper. The difference matters: the taxi company portal has **mutable fleet state that must survive navigation** (add a car on Cars, see it on Overview), and a layout route keeps the shell + provider mounted across child route changes. The Advertiser portal has no equivalent cross-page mutable state, so its simpler per-page-wrapper approach is fine there. If you add another portal with user-editable data spanning pages, use the layout-route pattern.

**`FleetContext` owns the fleet** — [FleetContext.tsx](../../../src/components/taxiCompany/FleetContext.tsx) holds `cars`/`drivers` state (seeded from the mock arrays) plus every fleet-wide dialog (Add Car, Add Driver, Report damage, Request maintenance), and is mounted once by the layout. Pages read via `useFleet()` and trigger dialogs with `openAddCar()` / `openAddDriver()` / `openDamageReport(carId?)` / `openMaintenanceRequest(carId?)`. **Don't add local `useState` for cars/drivers or duplicate these dialogs inside a page** — that's exactly the fragmentation the context exists to prevent.

**Add Car / Add Driver are genuinely functional, not stubs** — [AddCarDialog.tsx](../../../src/components/taxiCompany/AddCarDialog.tsx) and [AddDriverDialog.tsx](../../../src/components/taxiCompany/AddDriverDialog.tsx) build a real `Car`/`CompanyDriver` object and call `onAdd`; the context prepends it, so a new car immediately appears in the cars table, the fleet map, the screens inventory, the earnings table, and every KPI count. Deliberate, matching the user's demonstrated preference for real interactivity over decorative dialogs (see the map/dropzone fixes in [maps](../maps/SKILL.md) and [campaign-engine](../campaign-engine/SKILL.md)). Nothing persists past a page reload, but within a session it behaves like it works. **Prefer this local-state-append pattern over a pure toast stub for any new "create X" flow.**

**Components that render fleet data take it from `useFleet()`, never from the mock import.** [FleetMap.tsx](../../../src/components/taxiCompany/FleetMap.tsx) is the exception that proves the rule — it takes `cars` as an explicit prop (it's generic enough to be reused with a different car list), and it was originally a real bug: it imported `CARS` directly, so cars added via the dialog appeared in the table but never on the map. If you see a component here importing `CARS`/`DRIVERS` from `taxiCompanyMockData` instead of reading live state, that's almost certainly the same bug.

**Row actions preselect the right vehicle** — the per-row "Report damage"/"Request maintenance" menu items in [CarsTable.tsx](../../../src/components/taxiCompany/CarsTable.tsx) call `openDamageReport(car.id)`, while the fleet-level buttons in [FleetSupportCard.tsx](../../../src/components/taxiCompany/FleetSupportCard.tsx) call `openDamageReport(undefined)` to explicitly clear it. Both open the same shared [ActionDialog](../../../src/components/ActionDialog.tsx), which re-syncs its vehicle selection via a `useEffect` keyed on `open`/`defaultVehicle`. If you add a third entry point, always pass a vehicle id **or** an explicit `undefined` — omitting it silently reuses whatever was last selected.

**Shared pieces worth reusing rather than re-inlining:** `CarsTable` (used by both Overview and Cars with different `pageSize`/`height`), `CarDetailDialog` (vehicle + screen + driver info), `EarningsSummary` (the 4 payout tiles, `columns` prop), `FleetSupportCard` (Overview + Support), and `statusVariants.ts` (the `CarStatus`/`GpsStatus`/`ScreenStatus`/`DriverAssignmentStatus` → `StatusTagVariant` maps — import these instead of redefining the color mapping per page).

## Earnings page — what's derived vs. fixture

`EarningsPage` computes per-vehicle "hours pay" as `drivingHoursToday × DRIVER_HOURLY_RATE_USD` (imported from [earningsService](../../../src/services/earningsService.ts), not a magic number). The **monthly base ($30) and premium-area bonus ($20) are deliberately not multiplied across vehicles** — those are per-driver monthly components in the agreed formula (see [driver-app skill](../driver-app/SKILL.md)), and applying them per-car per-day would silently invent a different business rule and inflate fleet totals. The page states this in its subtitle. The summary tiles and payout history (`FLEET_EARNINGS`, `PAYOUT_HISTORY`) remain independent fixtures — they are **not** derived from the per-car numbers, so they won't move when you add a car. If the user asks for a truly consistent fleet earnings model, that's a real business-rule conversation, not a formatting fix.

## Shared components introduced here (now reused elsewhere)

- **`components/ActionDialog.tsx`** — generalized from a dialog that used to be defined locally inside `DriverDashboard.tsx`. Now shared by Driver (no `vehicleOptions`, single-vehicle context) and Taxi Company (`vehicleOptions` + `defaultVehicle`, multi-vehicle fleet). If Admin ever needs a similar "report an issue" flow, reuse this rather than writing a third copy.
- **`components/ImageUploadField.tsx`** — label + hidden file input + button/filename-chip, used by both image fields in `AddCarDialog` (papers) and both in `AddDriverDialog` (ID, license). Simpler than `CreateCampaignDialog`'s creative dropzone (no drag-and-drop) — that one wasn't refactored to use this component since campaign creative upload has different UX requirements (drag-and-drop, single larger asset); don't assume they should be unified without checking with the user first.
- **`src/data/lebanonRegions.ts`** — `LEBANON_REGIONS`, extracted so `CreateCampaignDialog`'s region-targeting chips and the taxi company signup's region select share one list instead of two independently-maintained copies.
