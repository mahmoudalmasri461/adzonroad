# AdzOnRoad Campaign Engine Skill

## What actually exists: a status model and a UI flow, not an engine

There is no scheduling/assignment engine anywhere in this codebase. "Campaign engine" in `CLAUDE.md` describes a future backend service that would dynamically assign campaigns to eligible screens by region/availability/schedule/health/GPS status — none of that logic exists. What exists today:

- **The status lifecycle** — `CampaignStatus` in [src/types/advertiser.ts](../../../src/types/advertiser.ts): `'Draft' | 'Pending Approval' | 'Scheduled' | 'Active' | 'Paused' | 'Completed' | 'Rejected'`. This is the authoritative status union for the advertiser portal — `StatusChip` (see [design-system skill](../design-system/SKILL.md)) is keyed off it. Admin's `AdminDashboard.tsx` uses a separate, unreconciled ad-hoc status representation (`StatusTag` + free-form `label`/`variant` pairs) — see [admin-portal skill](../admin-portal/SKILL.md) for that gap.
- **The creation flow** — [src/components/CreateCampaignDialog.tsx](../../../src/components/CreateCampaignDialog.tsx), a 7-step MUI `Stepper` (Info → Upload creative → Regions → Taxi count & duration → Dates & hours → Price review → **Submit**). Its open/close state lives in [CreateCampaignContext](../../../src/components/advertiser/CreateCampaignContext.tsx) (`CreateCampaignProvider` wraps every advertiser page via `AdvertiserLayout`), so any component under an advertiser page can trigger it with `useCreateCampaign().openCreateCampaign()` — the sidebar's "Create Campaign" nav item and every page's own "Create Campaign" button all call the same context, not separate local dialog state. **Don't fork the dialog or add a second local `dialogOpen` state** per entry point — always go through the context.
  - **There is no payment step.** The last step used to collect a card number/expiry/CVC that went nowhere; the user explicitly asked for it to be replaced with a "submit inquiry" flow instead, since there's no real online payment (see [billing skill](../billing/SKILL.md)). The final step now just confirms the campaign will be reviewed by the team, and the button reads "Submit inquiry" (fires a `useToast` confirmation, no form fields). **Don't re-add card/payment fields here** unless the user asks for real payment processing again.
  - The "Upload creative" step has a real, working dropzone — a hidden `<input type="file">` + click-to-browse + drag/drop handlers, storing the selected `File` in local state and showing its name/size with a Remove option. There's still no backend to upload to (nothing is actually sent anywhere), but the interaction itself is real, not decorative — don't regress it back to a static box.
  - The "Budget (USD)" field strips non-digit characters on every keystroke (`value.replace(/[^0-9]/g, '')`) — it used to accept arbitrary text. Keep any future numeric-input field on this same sanitize-on-change pattern rather than relying on `type="number"` alone (HTML number inputs still let through `e`/`+`/`-`).
  - "Dates & hours" uses `@mui/x-date-pickers` (`DatePicker`/`TimePicker`, `AdapterDayjs`) instead of native `<input type="date">`/`type="time"` — the native time input's browser-default UI was flagged as looking dated. `dayjs` and `@mui/x-date-pickers` are real dependencies now (see `package.json`), added specifically for this.
- **The pricing formula** lives in [src/services/pricingService.ts](../../../src/services/pricingService.ts) (`estimateCampaignPrice`) — $20 per taxi per second of creative duration for the standard 8hr/day window, plus a flat $150 surcharge per region beyond the first. This was reverse-derived from and verified against the three published tiers (5 taxis/15s = $1,500, 10 taxis/15s = $3,000, 10 taxis/30s = $6,000 — all resolve to exactly $20/taxi/second) and is the **single source of truth** for both `CreateCampaignDialog`'s live estimate and the Homepage pricing section's displayed tier prices (`Homepage.tsx` imports `PRICING_TIERS` from the same service and formats them with `formatCurrency`) — they can no longer drift apart. The per-region surcharge amount is an implementation choice, not a verified business figure (the three known anchors are all single-region) — flag it to the user if a real number is specified later.
- **Valid creative durations are `15 | 30 | 45 | 60 | 75 | 90` seconds only** (`CreativeDurationSeconds` in `pricingService.ts`, mirrored by `CreativeDuration` in `types/advertiser.ts`) — **10 seconds is not a valid option**, the user explicitly corrected this. If you see `10` anywhere as a duration value or option, it's a bug; the two mock `CREATIVES` entries that used to say `10` were moved to `15`.
- **Taxi count in the dialog is capped at the real available fleet**, not an arbitrary number — `TOTAL_AVAILABLE_TAXIS` in `CreateCampaignDialog.tsx` sums `activeTaxis` across `REGIONS` in `advertiserMockData.ts` (currently 216), and the slider's `max` plus its label ("Taxi count — N of 216 available") both reference it. If the underlying region data changes, this cap updates automatically — don't hardcode a taxi-count max again.
- **Read-only campaign displays** — `CampaignTable.tsx` (DataGrid, search/status/region filters via `useSearchFilter` + `FilterBar`, row-action menu with a real `ConfirmationDialog` on Archive, all other actions stubbed via `useToast`) and `CampaignProgressCard.tsx` (single delivery-progress row), both driven by the static `CAMPAIGNS` array in `src/data/advertiserMockData.ts`.

## If asked to change the pricing model further

Edit `estimateCampaignPrice` in `pricingService.ts` — both `CreateCampaignDialog` and `Homepage.tsx` consume it, so a change there propagates everywhere automatically. Don't reintroduce a second, independent pricing calculation anywhere else.

## If asked to build the real assignment engine

That's backend work with no existing scaffold — there is no backend project in this workspace. Treat it as a from-scratch architecture task (ASP.NET Core is the stated target stack per `CLAUDE.md`, but nothing has been started) rather than something to bolt onto the frontend mock data.
